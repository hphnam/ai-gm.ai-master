- `ingest/refresh.py:_ensure_tables` adds `per_fold_mase VARCHAR` and `n_folds INTEGER` to the `CREATE TABLE` DDL, plus two `ALTER TABLE ladder_selection ADD COLUMN IF NOT EXISTS ...` statements so an existing on-disk store picks them up idempotently (verified: DuckDB 1.5.4 supports `ADD COLUMN IF NOT EXISTS`).

## Deviations from the spec

1. **Ellel's winner is `rung3_gbm`, not a Rung-4 foundation model.** The spec's G12.9c section speculates "if Chronos-2 wins Ellel, that is a genuine finding" and frames the decision-log entry around that outcome. The actual run shows classical gradient boosting winning (MASE 0.533 vs Chronos-2-exo's 0.570), with Chronos-2-exo a close second. This does not fail any acceptance criterion: the milestone gate is still met, the cap hypothesis is still correctly retired, and "a rung not being adopted on Ellel is a valid gate outcome, not a failure" per the spec's own stop-condition note. But the finding to record in a decision log is "GBM, not Chronos-2, wins Ellel" rather than the foundation-model story the spec anticipated.
2. **No archival decision log exists to echo to.** The spec says "if Nam is maintaining a synced copy, echoed to the decision log on the archival branch" (`feat/chronos2-promotion`). I checked: that branch's decision-log/report files were removed in prior commits (`c8bd2c9`, `05935c6`, "chore: remove remaining PRJ93_ working docs"). There is currently no decision-log file on either branch to echo into. All decisions are recorded in `brain/FLAGS.md` and this report only, as instructed for the fallback case; flagging this so a human can decide whether to recreate an archival log.
3. **FLAG-G12.9-2's exact mechanism differs from the spec's description.** The spec says "`wrap.evaluate` cannot serve a `rung3_gbm` model (KeyError on the predictor resolution path)". Tracing the actual registry code shows the real gap is `rung3_global_gbm` (the pooled/global GBM variant, distinct from `rung3_gbm`), and the actual exception is `ValueError`, not `KeyError` (`conformal.wrap._predictor` raises `ValueError(f"unknown model {model_name!r}")` on a dict-lookup miss). I recorded the verified mechanism in `FLAGS.md` rather than the spec's paraphrase, since it's the more useful description for whoever eventually fixes it.
4. **One transient DuckDB internal crash during the weather pull**, unrelated to any code change here: `python -m ingest.exog_weather` raised `duckdb.InternalException: Attempted to access index 0 within vector of size 0` partway through the `hindcast`/`leadmatched` basis pulls for the new cells. Isolating it showed the individual Open-Meteo fetches were fine (valid, non-empty, no-NaN frames); a second identical run completed successfully and left all three bases fully populated with `observed != hindcast` (a real forecast-vs-reanalysis difference) confirmed True. No code change was made for this: it did not reproduce on retry and does not appear related to G12.9's changes (a fresh DuckDB engine issue would need separate investigation if it recurs).
5. **`EVENT_ONLY_VENUES` required no code split.** The spec asks to "reconsider... if it currently does double duty... split the two". Reading every call site showed it never gated the ladder cap in the first place (`MAX_RUNG` always did that, as a fully separate dict), so there was nothing to split. I documented this finding in both `config.py`'s docstring and this report rather than making a no-op code change.
6. **Environment note, not a G12.9 regression:** `.venv-forecast` does not have `prophet` installed (unlike whatever environment produced the previously-committed ladder reports, which show live Prophet numbers). The regenerated reports correctly show `rung2_prophet: backend not installed` for all three venues. This is an environment difference, not something introduced by this work, and Prophet is a comparison row only (never a served model) so it has no effect on any adopted rung. Also pre-existing and unrelated to this spec: `rung4_chronos2_exo` raises a `ValueError` in the **static** (not rolling/milestone) evaluation regime for every venue that has it available, confirmed identical in the pre-G12.9 committed `beer_hall` and `two_river_taps` reports (`git show HEAD:...`), so not a regression from the venue-scoped covariate change.
