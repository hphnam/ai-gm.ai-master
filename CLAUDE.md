
## Architecture

- Monorepo: `apps/api` (NestJS) and `apps/web` (Next.js App Router). npm workspaces + Turborepo.
- API modules are feature-based under `apps/api/src/modules/<domain>`. One module per domain (auth, chat, chat-starters, compliance, embeddings, indexer, notifications, tasks, whatsapp, etc.).
- Knowledge pipeline: Reducto extracts documents → Voyage embeds (`voyage-3.5`) and reranks (`rerank-2`) → stored in Postgres via Prisma.
- WhatsApp integration via Twilio Conversations API. Webhook at `/webhooks/twilio/conversations` (urlencoded, X-Twilio-Signature HMAC-SHA1). New users onboard via signed-link DM; existing users link a phone with a web-entered confirmation code.
- Realtime via Socket.io with Redis adapter; background jobs via BullMQ. Per-user events (`task.upserted`, `notification.created/updated/reply.created`) fan out to private user rooms; org-scoped events (`doc.updated`, `gap.updated`, `expiry.upserted`, `whatsapp.invite.updated`) fan out to the org room.
- Notes (in-app notifications) support flat reply threads — `GET/POST /notifications/:id/replies`, scoped to the original recipient + author. System-authored notes (compliance reminders) are read-only. Wave 4 role gate on `POST /tasks`: staff = self-only, manager + owner = anyone.

## Key Decisions

- Auth: better-auth with multi-org support. Org membership gates knowledge access.
- Phone verification uses WhatsApp OTP (not SMS) — see `apps/api/src/modules/phone`.
- No console/dev-fallback transport modes exist. SMTP is required at boot (all 5 vars — `assert-auth-env.ts` fail-fasts without them) and every email sends live; SMS/WhatsApp sends fail loudly (`whatsapp-not-configured` / logged error) when Twilio creds are absent instead of pretending to deliver. The `*_DRIVER_OVERRIDE` flags are gone — don't reintroduce them. Twilio is the sole SMS/WhatsApp transport (Infobip fully removed).
- Embeddings stay on Voyage (not OpenAI). Don't swap without re-embedding the corpus.
- Probes (`probe:eval`, `probe:section`) are the quality gate after any retrieval/embedding change. `probe:chat` (`apps/api/scripts/probe-chat.ts`) is the agent-behaviour gate after any chat prompt/tool/routing change — it drives the real `buildGmAgent` + a live model call against a fake dispatcher (no DB/network), asserting the tool-call log (hard gate) + loose text regexes for citation/role-scoping/no-data/incident/tools-first behaviour. Key-gated (skips + exits 0 without `ANTHROPIC_API_KEY`).
- Background queues: `nudges` (stock cutoff pings, `NUDGE_CRON_DISABLED=1` to skip), `task-reminders` (Wave 1 reminders, `TASK_REMINDER_CRON_DISABLED=1` to skip), `expiry-scheduler` (Wave 2 compliance reminders at 30/7/1/overdue windows, `EXPIRY_SCHEDULER_DISABLED=1` to skip), and `chat-starters` (Wave 3 per-venue rotating /chat landing prompts, regenerated every 3 days, `CHAT_STARTERS_CRON_DISABLED=1` to skip the cron; `CHAT_STARTERS_GENERATOR_DISABLED=1` to skip the Haiku call without disabling the cron). The Wave 2 expiry extractor runs on each upload via the ingest pipeline — set `EXPIRY_EXTRACTOR_DISABLED=1` to skip the classifier call. All BullMQ jobs register on `onApplicationBootstrap` in their processors.
- Document version reconciliation: on every new upload (not re-ingest), after ingest completes, `ReconcileService.detectAndSupersede` (`apps/api/src/modules/docs/reconcile.service.ts`) finds the closest live doc of the same `documentTypeId` in the same venue scope by cosine against the new row's stored embedding. Above `RECONCILE_AUTO_CONFIDENCE` (0.86) the predecessor is archived in place: `supersededAt` + `supersededById` stamped, `version` bumped on the successor, and the predecessor's heavy derived rows (SearchableEntity, sections/chunks, tabular, Checklist) deleted so it leaves retrieval, with its active `ExpiryRecord`s set to `dismissed` (the successor's ingest re-extracts fresh ones). The `KnowledgeItem` row + content are kept for version history. Live docs are `supersededAt IS NULL`; the docs list + inbox filter on it by default. Skips the re-ingest path (`preserveDocumentTypeId`) since that's an explicit in-place update, and is fully off with `DOC_RECONCILE_DISABLED=1`. Best-effort — a reconcile failure never fails the upload. Manual reconcile: `POST /docs/:id/supersede` (manager-only) body `{ replaces }` marks `:id` as superseding `replaces` — a human's explicit choice bypasses the auto guards but adds strict org-ownership validation on both ids (409 `reconcile-conflict` on same-id/already-archived). Undo: `POST /docs/:id/unsupersede` (manager-only, rate-limited, 409 `reconcile-conflict` when `:id` isn't archived) clears the stamps, rolls the successor's `version` back to the predecessor's, and re-ingests `:id` from its stored content (no original file ⇒ tabular rows aren't rebuilt) so it re-enters retrieval; `ReconcileService.unsupersede` runs the locked tx + realtime fanout, `DocsService.unsupersedeManually` validates + fires the re-ingest. Operator UI: DTOs expose `version` / `supersededAt` (+ `supersededBy` / `supersedes` `{id,title}` on detail); the library `status=archived` filter surfaces superseded docs; doc-detail shows an "Archived → replaced by «…»" banner with Restore on archived docs and a "Replaces an earlier version · View previous" line + a "Replace an older version" picker (`supersede-picker-modal.tsx`) on live ones. Backfill pre-existing duplicates with `apps/api/scripts/reconcile-duplicates.ts` (dry-run by default; `--apply` supersedes only pairs clearing the same title + compliance guards as the auto path — note its similarity default is 0.80, below the auto path's 0.86; `--include-compliance` relaxes the expiry guard). The locked archive lives in the exported `archiveWithinTx` so the endpoint, auto path, and script share identical logic + the FOR-UPDATE concurrency guard.
- Unread-notes email digest: daily BullMQ cron (`note-digest` queue, 07:00 UTC via `upsertJobScheduler` with explicit `tz: 'UTC'` — NOT queue.add+repeat, so a future cron change replaces the old schedule instead of double-scheduling) emails each user one per-org summary of notes still unread from the last 24h window. The window is anchored to the 07:00 boundary (`digestWindowEnd`), not processing wall-clock, so a late-drained tick tiles exactly — each note appears in at most one digest, stateless (no emailed-at stamp). Recipients must have `emailVerified`, a well-formed non-synthetic email (`isDigestableEmail` drops malformed addresses + `@phone.gm-ai.local`), AND still be an org member at send time (batched `organizationMember` recheck — notification rows outlive membership-only removal) — note bodies are org-internal content, never sent to an unproven mailbox or an ex-member; a null-named author falls back to their email only if it's non-synthetic. Scan is served by the `[status, createdAt]` index (migration `20260707000000`). Each note links to `PUBLIC_APP_URL/notes/<id>` — the canonical note deep link: `/notes/[id]` (web) resolves via `GET /notifications/:id` (recipient-scoped), opens the inbox sheet on the right surface (chat category → conversation thread with the author, else Alerts tab focused) and settles on `/chat`. Inbox open/focus state lives in `InboxProvider` (`components/shell/inbox-provider.tsx`, mounted in AppShell) so pages can drive the sheet, not just the bell. Disable the cron with `NOTE_DIGEST_CRON_DISABLED=1`. Email templates are plain-HTML with `escapeHtml` (same pattern as invitation email); send is best-effort per recipient via `modules/email/mailer.ts`.
- Direct Redis cache: Wave 3 `chat-starters` writes a per-venue, per-role payload to `chat:starters:<orgId>:<venueId>:<staff|manager>` with an 8-day TTL via a dedicated ioredis client on `REDIS_URL` (separate from BullMQ job state and Socket.IO adapter). One Haiku call per venue produces BOTH role sets: staff get operational-ritual prompts only (opening/closing/daily checklists, stock, prep, logging, incident reporting); managers additionally get commercial/compliance/oversight prompts. Generation mines role-split recent chat questions PLUS `SearchAnalytics` `no-data` "unmet questions" (minus `DismissedNoDataQuery` noise), bucketed by the asker's `OrganizationMember.role` (null/unknown asker → staff). The `GET /chat-starters` controller derives audience from the caller's session role (`audienceForRole`, owner→manager); the fanout uses `upsertJobScheduler` so a cadence change replaces the old schedule. Flush by `DEL` on that key pattern; absent keys fall back to a role-appropriate generic prompt list inline.
- Third-party integrations (Square today; more later): generic `Integration` model holds encrypted per-org credentials. Encryption is AES-256-GCM with a per-record random salt + IV and HKDF-derived encryption key; ciphertext is version-tagged on disk (`v1:<base64>`) so future key/cipher rotations are non-breaking. The master key comes from `INTEGRATION_TOKEN_KEY` and MUST be prefixed `hex:` (64 hex chars) or `base64:` (44 base64 chars decoding to 32 bytes) — raw passphrases are rejected at boot. Generate one with `openssl rand -hex 32`. Providers self-register tools at `onModuleInit` against `IntegrationRegistry`; multiple providers may claim the same tool name (capability) and dispatch routes per-org via `Integration.provider`. Each provider declares a `domain` (`pos | accounting | crm | brewery | other`) and the connect endpoint refuses a second provider in the same domain for the same org. `validateCredentials` on a provider pings the vendor at connect-time so bad PATs are rejected before persistence. `ToolDispatcher` falls through to the registry on built-in tool miss, and `buildAiSdkTools` concatenates provider tool definitions onto `TOOL_DEFINITIONS`. New integrations: drop a module under `apps/api/src/modules/integrations/<provider>/`, implement `IntegrationProvider`, `register()` against the registry — no edits to `chat-tools.ts`. Venues map to a POS location via `Venue.squareLocationId`. Connect endpoint: `POST /integrations/:provider/connect-pat` (manager-only, rate-limited 10/15min/org); OAuth not yet wired but schema is OAuth-shaped (`authMode`, `refreshTokenCipher`, `tokenExpiresAt`). Per-tool per-org rate limit: 120/min (`TOOL_INVOCATION_LIMITER` in `integration-registry.ts`).
- Breww integration (`apps/api/src/modules/integrations/breww/`, domain `brewery`): read-only surface over the Breww public API (DRF-style REST at `breww.com/api/`, bearer keys prefixed `BRW.`, page/page_size pagination) — `brewery_list_batches` + `brewery_list_products` (staff), `brewery_list_purchase_orders` + `brewery_get_product_margins` (manager). The margins tool reads `/order-lines/` per-sale `product_production_cost`/`product_packaging_cost`/`margin_*` — the authoritative brewery-side production cost, and the COGS fallback when the POS catalog has no unit costs. No SDK — plain `fetch` in `breww.service.ts` (15s timeout; Breww has no `icontains` filter, so product-name matching fetches one name-ordered page and filters case-insensitively in code); connect via the generic `POST /integrations/breww/connect-pat` (validates against `/business-details/`) or the Settings card (entry in web `use-integrations.ts` `INTEGRATION_PROVIDERS`). NOT yet exercised against a live Breww account — first connect with a real key is the remaining verification.
- Square SDK (44.x) serializes UNSET optional enum query params as empty strings (`?sort_order=`) which Square 400s on GET list endpoints (devices, payouts, payments) — `scrubbingFetch` in `square-client.ts` strips empty-valued params for every call; don't remove it on SDK upgrade without re-probing (`apps/api/scripts/probe-square-endpoints.ts`). Related quirks: `vendors.search` requires a non-empty `filter` (listVendors always sends a status, default ACTIVE), and Square answers 401 "Merchant not onboarded to Appointments" for bookings on accounts without that product — `isFeatureNotOnboarded` in `square.service.ts` keeps that from tripping `markError` (which would flip the whole integration to 'error' and disable every Square tool).

- Business-aware chat: the system prompt (`apps/api/src/modules/chat/system-prompt.ts`) is parameterized, not vertical-hardcoded. Per-org business profile lives on `Organization.metadata.profile` (no column/migration — `OrganizationProfileSchema` in `types/organization.ts`: businessType, description, goals, constraints, country, currency) and is edited at `GET/PUT /org/profile` (owner/manager; `OrganizationModule`). `POST /org/profile/describe` (owner/manager, Redis 10/min/org, 503 `generate-failed`) drafts the `description` with a Haiku pass over org name + businessType + venues — the Settings form's "Generate/Rewrite with AI" button. Onboarding also prefills `description` from Google's `editorialSummary` (`places.normalize.ts`) when the user hasn't written one. `buildGmAgent` injects three dynamic system blocks: `<business_profile>` (persona/domain), `<operating_context>` (currency + emergency number derived from `country`, defaulting GB/£/999 so an empty profile behaves as before), and `<integrations>` (human-readable active integrations from `IntegrationRegistry.describeActiveIntegrations` — when none are connected the agent is told there are no live numbers). Chat + scheduled-report paths both load profile via `loadOrganizationProfile(orgId)`. The web Settings → Organization page has a Business profile form (`components/organization/business-profile-form.tsx`, hook `lib/hooks/use-org-profile.ts` — hand-written, NOT in the orval client; run `npm run api:generate --workspace=web` to fold it in).
- Chat tool-call UI: the agent's work renders as a step trace, not chips/accordions. While streaming, `AgentTraceLive` (`components/chat/agent-trace.tsx`) shows the ordered tool sequence — settled steps get a check + past-tense label (`toolDonePhrase` in `tool-labels.ts`), the active step a pulsing dot + elapsed; consecutive same-tool calls collapse into one step (`classifyAssistantParts` in `chat-message.tsx`) and the trace stays mounted above the streaming answer. Once settled (and on reload) it collapses to a "Ran N steps · Xs" disclosure (`AgentTraceDisclosure`; elapsed is client-captured, so reload shows steps only). Reload rehydrates EVERY persisted `toolCallLog` entry as a settled tool part (`message-mapping.ts`) — deliverable tools render their card, KB parts feed the "no sources cited" warning, the rest feed the trace. Zero-tool turns render no trace.
- Agent memory: per-org persistent memory via the Anthropic `memory_20250818` provider-defined tool (`@ai-sdk/anthropic`). Stored as a path→content map on `Organization.metadata.memory` (no migration), sandboxed to `/memories` with size caps. Pure command engine `applyMemoryCommand` in `modules/organization/agent-memory.ts` (view/create/str_replace/insert/delete/rename); DB read-modify-write in `agent-memory.store.ts` (`handleMemoryCommand`, transactional so it never clobbers the sibling `profile` key). Wired into `buildGmAgent` via the optional `memoryExecute` closure — enabled for interactive chat only (NOT headless scheduled reports), and the `<memory>` prompt block is injected only when the tool is present. Disable org-wide with `AGENT_MEMORY_DISABLED=1`. Memory is for durable operating preferences/facts — NOT a replacement for the KB (SOPs → `save_knowledge_doc`), tasks, or notes; the `<memory>` prompt block enforces precedence (KB/live tools/owner always override memory; memory is never cited and never gates capability) so the two stores can't clash. Both `handleMemoryCommand` and `OrganizationService.updateProfile` write their own metadata subkey via `jsonb_set` under a `SELECT … FOR UPDATE` row lock, so concurrent memory/profile writes never lose updates. Staleness hygiene: `MemoryReconcileModule` (BullMQ `memory-reconcile` queue) prunes memory notes the KB now contradicts/covers via a conservative Haiku pass — a nightly fanout over orgs with non-empty memory PLUS a debounced per-org trigger (`MemoryReconcileTrigger.onKbChanged`, 5-min coalesce) fired when a doc reaches `ready` or is superseded (`docs.service` + `reconcile.service`). Read-time precedence already prevents stale answers; reconcile only purges lingering notes. Flags: `MEMORY_RECONCILE_CRON_DISABLED=1` (cron + trigger), `MEMORY_RECONCILE_GENERATOR_DISABLED=1` (skip the Haiku call).

- Role-based agent data scoping: staff are scoped to operational data; financial/commercial figures + cross-person PII are manager/owner-only. Classification is by CAPABILITY, not user phrasing. Integration tools carry a `minRole` (`integration-provider.ts`) that is **fail-closed** — the registry treats an unstamped integration tool as `manager` (`DEFAULT_TOOL_MIN_ROLE`), so a newly added tool is withheld from staff until a provider explicitly opts it into a staff allowlist (Square's is `STAFF_VISIBLE_POS_TOOLS` in `square.tools.ts` — items/inventory/locations/bookings/devices/shift-listing). Two hard layers + one semantic: (1) `IntegrationRegistry.getToolSurfaceForProviders(activeProviderIds, userRole)` filters manager-only tools out of a staff user's tool surface; (2) `IntegrationRegistry.dispatch` re-checks `roleMeetsMinRole` and hard-denies before the vendor call, so a jailbroken model still can't reach the data; (3) the `DATA ACCESS BY ROLE` + `SECURITY` blocks in `system-prompt.ts` make the model decline categories gracefully, refuse KB/spreadsheet-sourced financials too, refuse indirect reconstruction, and resist role-escalation/injection. Shift-LISTING tools are staff-visible (rota is team info) but `redactShiftPayForStaff` (`square.provider.ts`) nulls `hourlyRate`/`estimatedCost` per row for staff; labour-COST summaries stay manager-only. Built-in tools keep their existing per-tool dispatcher gates (`add_supplier_note`, `save_knowledge_doc`, `create_task` cross-assign, `record_pricing_recommendation`). Role reaches the agent as `DispatchContext.userRole` (defaults `staff`); scheduled reports run with the creator's live role, chat-core/WhatsApp researchers touch no integration tools. Coverage: `integrations/role-scoping.spec.ts`.

- Per-member venue scoping: orthogonal to role scoping. `OrganizationMember.venueIds String[]` (migration `20260709000000`; empty = ALL venues, non-empty = restricted to those venue ids, OWNERS always resolve to all regardless). Staff AND managers can be scoped; owners never. Semantics + helpers live in `apps/api/src/modules/auth/venue-scope.ts` (`isVenueScoped`/`canAccessVenue`/`resolveAccessibleVenueIds`; owner-or-empty ⇒ all). Captured on invite: `venueIds` on `InviteBodySchema` + `CreateInviteInputSchema` (whatsapp), validated by `sanitizeVenueScope` (drops unknown/cross-tenant ids, forces `[]` for owner) in `invitations.service.ts`, carried invite→membership on accept (`acceptInvitation`) and both phone paths (`consume-phone-invite.ts`, `whatsapp-onboarding.service.ts`). Editable post-hoc via `PATCH /org/members/:userId/venues` (`updateMemberVenues`, owner/manager, same permission matrix as removeMember — owner edits managers+staff, manager edits staff only, never an owner/self). Enforcement is fail-safe in depth: membership rides `venueIds` via customSession (`auth.config.ts`) → `req.membership.venueIds` (`org-context.middleware.ts`); a GLOBAL `VenueScopeGuard` (`venue-scope.guard.ts`, registered `APP_GUARD` in `app.module.ts`) hard-denies (404 `venue-not-found`) any request whose `venueId` target (param→query→JSON-body) is out of scope; `VenuesService` list/get/update/updateProfile/updateSquareLocation take a `scope` and filter/deny; the two multipart venue endpoints (chat image upload, `POST /docs/upload`) keep an explicit `canAccessVenue` check because multer parses the body AFTER guards run. `sanitizeVenueScope` is fail-closed: a non-empty selection that resolves to zero grantable venues throws `invalid-venue-scope` (400) rather than silently widening to all; and a venue-scoped ACTOR can only grant venues within their own scope (intersection). The web venue switcher only shows accessible venues (`GET /venues` is scope-filtered), so scoped users can't select out-of-scope venues in the UI. The comprehensive backstop is a **Prisma client extension driven by AsyncLocalStorage** (`apps/api/src/database/venue-context.ts`): `OrgContextMiddleware` wraps the rest of every request in `runWithVenueContext({role, venueIds})`, and the extension auto-narrows EVERY query on the 12 venue-bearing models (Task/Report/ScheduledReport/ExpiryRecord/KnowledgeItem/IncidentLog/PricingRecommendation/VenueContact/ChatConversation/MockStock/MockPurchaseOrder + Venue-by-`id`) to the scoped member's venues — reads get `venueId IN (...)` (plus `OR venueId IS NULL` for models whose null rows are org-wide), `findUnique` is post-filtered (out-of-scope ⇒ null / throw on OrThrow), `updateMany`/`deleteMany` are narrowed (strict, no org-wide rows), and `create`/`createMany`/`upsert` reject an explicit out-of-scope `venueId`. It is a no-op for owners/unscoped members and for all non-request code (jobs/cron/CLI run with no store ⇒ full access). Kill-switch `VENUE_CONTEXT_DISABLED=1`. CRITICAL GOTCHA — do NOT "simplify" this to a single global `base.$extends(...)`: Prisma runs an extension's `query` hook in a DETACHED async context, so `AsyncLocalStorage.getStore()` returns null INSIDE the hook (verified). The scope is therefore captured in the extension's CLOSURE (`venueScopeExtension(scope)`) and a per-request scoped client is built lazily and cached on the ALS store; the `prisma` lazy Proxy calls `resolveClientForRequest()` on every property access (which DOES run inside the request's ALS frame) to pick the scoped vs base client. A global `$extends` reading ALS in the hook silently no-ops (fails open). So omitting `venueId` on a list, or hitting a resource by its own id, is now venue-isolated at the DB layer without per-service plumbing. All op families are covered: reads (findMany/findFirst/count/aggregate/groupBy + findUnique post-filter), bulk writes (updateMany/deleteMany/updateManyAndReturn narrowed), single writes (update/delete/upsert push a strict venue filter into the unique where — Prisma 4.5+ accepts extra non-unique filters on unique ops, so an out-of-scope target matches nothing), and creates (create/createMany/createManyAndReturn reject an explicit out-of-scope venueId). ONLY CAVEAT: raw SQL (`$queryRaw`/`$executeRaw`, e.g. vector retrieval) bypasses the extension — those paths are org-scoped by design + gated at chat entry. Verified end-to-end against the live DB (scoped count → 0, owner → full, survives awaits, transactions inherit scope). `sanitizeVenueScope` is fail-closed: a non-empty selection that resolves to zero grantable venues throws `invalid-venue-scope` (400) rather than silently widening to all; and a venue-scoped ACTOR can only grant venues within their own scope (intersection). Web: `VenueAccessPicker` + `MemberAccessDialog` (invitations/), `useUpdateMemberVenues`; picker hidden for single-venue orgs. Coverage: `auth/venue-scope.spec.ts`, `database/venue-context.spec.ts`.

- SMS onboarding: the invite SMS embeds the single-use PIN in the link's URL FRAGMENT (`/onboard?t=<token>#c=<pin>`, `invite.service.ts`) so it never hits server/CDN logs; `onboard-body.tsx` resolves + scrubs the fragment before mounting the OTP form (`?c=` still accepted for pre-fragment links), auto-verifies on load, and falls back to manual entry on failure (`onboard/page.tsx` sets `referrer: no-referrer`; `phone-otp-form.tsx` holds the auto-verify effect). After verify, a REQUIRED name step (`onboard-body.tsx`) persists `User.name` via `authClient.updateUser` before `/chat`, so the agent has a real identity (phone-only users' `User.email` is a synthetic `ph+<e164>@phone.gm-ai.local` placeholder — better-auth needs a unique email; it's suppressed in the members list, which shows `phoneNumber` instead — `OrgMemberSchema` now returns `email:nullable` + `phoneNumber`). Member removal: `DELETE /org/members/:userId` (`members.controller.ts` → `InvitationsService.removeMember`, owner/manager gated). Permission matrix: owner removes managers + staff; manager removes staff only; never yourself or an owner. The three invite FKs that would block a User delete (`WhatsappInvite.targetUserId`/`issuedByUserId`, `Invitation.inviterId`) are detached in the tx first; all other User relations are Cascade/SetNull. Web: `MembersList` Remove button (role-mirrored visibility) + `ConfirmDeleteDialog`, hook `useRemoveOrgMember`.

## Review Gate

Before declaring any code-edit task complete in `apps/api/src/` or `apps/web/src/`, spawn `code-reviewer` and `security-reviewer` (parallel — one message with multiple Agent tool blocks). For doc or API-contract changes, also spawn `doc-reviewer`. Surface every HIGH/MEDIUM finding before closing the work.

Skip only for: pure doc edits, formatting-only changes, dependency bumps with no code impact, single-line config knob changes.

## Don'ts

- Never modify existing Prisma migrations under `apps/api/prisma/migrations/`. Add a new one.
- Don't edit `apps/web/src/generated/**` (orval-generated API client).
- `docs/` xlsx files are runtime canaries for the document-intelligence pipeline, not dev seed data.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
