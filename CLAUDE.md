# Project Instructions

## Commands

```bash
# Workspace-wide (Turborepo)
npm run dev                                       # all apps
npm run build
npm run lint

# API (apps/api — NestJS + Prisma)
npm run dev --workspace=api                       # nest start --watch
npm run db:migrate --workspace=api                # prisma migrate dev
npm run db:generate --workspace=api               # prisma generate
npm run db:studio --workspace=api

# Tests (node built-in runner)
node --import tsx --test path/to/file.spec.ts
```

## Architecture

- Monorepo: `apps/api` (NestJS) and `apps/web` (Next.js App Router). npm workspaces + Turborepo.
- API modules are feature-based under `apps/api/src/modules/<domain>`. One module per domain (auth, chat, chat-starters, compliance, embeddings, indexer, notifications, tasks, whatsapp, etc.).
- Knowledge pipeline: Reducto extracts documents → Voyage embeds (`voyage-3.5`) and reranks (`rerank-2`) → stored in Postgres via Prisma.
- WhatsApp integration via Twilio Conversations API. Webhook at `/webhooks/twilio/conversations` (urlencoded, X-Twilio-Signature HMAC-SHA1). New users onboard via signed-link DM; existing users link a phone with a web-entered confirmation code.
- Realtime via Socket.io with Redis adapter; background jobs via BullMQ. Per-user events (`task.upserted`, `notification.created/updated/reply.created`) fan out to private user rooms; org-scoped events (`doc.updated`, `gap.updated`, `expiry.upserted`, `whatsapp.invite.updated`) fan out to the org room.
- Notes (in-app notifications) support flat reply threads — `GET/POST /notifications/:id/replies`, scoped to the original recipient + author. System-authored notes (compliance reminders) are read-only. Wave 4 role gate on `POST /tasks`: staff = self-only, manager + owner = anyone.

## Key Decisions

- Auth: better-auth with multi-org support. Org membership gates knowledge access.
- Phone verification uses WhatsApp OTP (not SMS) — see `apps/api/src/modules/phone`.
- Embeddings stay on Voyage (not OpenAI). Don't swap without re-embedding the corpus.
- Probes (`probe:eval`, `probe:section`) are the quality gate after any retrieval/embedding change.
- Background queues: `nudges` (stock cutoff pings, `NUDGE_CRON_DISABLED=1` to skip), `task-reminders` (Wave 1 reminders, `TASK_REMINDER_CRON_DISABLED=1` to skip), `expiry-scheduler` (Wave 2 compliance reminders at 30/7/1/overdue windows, `EXPIRY_SCHEDULER_DISABLED=1` to skip), and `chat-starters` (Wave 3 weekly per-venue rotating /chat landing prompts, `CHAT_STARTERS_CRON_DISABLED=1` to skip the cron; `CHAT_STARTERS_GENERATOR_DISABLED=1` to skip the Haiku call without disabling the cron). The Wave 2 expiry extractor runs on each upload via the ingest pipeline — set `EXPIRY_EXTRACTOR_DISABLED=1` to skip the classifier call. All BullMQ jobs register on `onApplicationBootstrap` in their processors.
- Document version reconciliation: on every new upload (not re-ingest), after ingest completes, `ReconcileService.detectAndSupersede` (`apps/api/src/modules/docs/reconcile.service.ts`) finds the closest live doc of the same `documentTypeId` in the same venue scope by cosine against the new row's stored embedding. Above `RECONCILE_AUTO_CONFIDENCE` (0.86) the predecessor is archived in place: `supersededAt` + `supersededById` stamped, `version` bumped on the successor, and the predecessor's heavy derived rows (SearchableEntity, sections/chunks, tabular, Checklist) deleted so it leaves retrieval, with its active `ExpiryRecord`s set to `dismissed` (the successor's ingest re-extracts fresh ones). The `KnowledgeItem` row + content are kept for version history. Live docs are `supersededAt IS NULL`; the docs list + inbox filter on it by default. Skips the re-ingest path (`preserveDocumentTypeId`) since that's an explicit in-place update, and is fully off with `DOC_RECONCILE_DISABLED=1`. Best-effort — a reconcile failure never fails the upload. Manual reconcile: `POST /docs/:id/supersede` (manager-only) body `{ replaces }` marks `:id` as superseding `replaces` — a human's explicit choice bypasses the auto guards but adds strict org-ownership validation on both ids (409 `reconcile-conflict` on same-id/already-archived). Undo: `POST /docs/:id/unsupersede` (manager-only, rate-limited, 409 `reconcile-conflict` when `:id` isn't archived) clears the stamps, rolls the successor's `version` back to the predecessor's, and re-ingests `:id` from its stored content (no original file ⇒ tabular rows aren't rebuilt) so it re-enters retrieval; `ReconcileService.unsupersede` runs the locked tx + realtime fanout, `DocsService.unsupersedeManually` validates + fires the re-ingest. Operator UI: DTOs expose `version` / `supersededAt` (+ `supersededBy` / `supersedes` `{id,title}` on detail); the library `status=archived` filter surfaces superseded docs; doc-detail shows an "Archived → replaced by «…»" banner with Restore on archived docs and a "Replaces an earlier version · View previous" line + a "Replace an older version" picker (`supersede-picker-modal.tsx`) on live ones. Backfill pre-existing duplicates with `apps/api/scripts/reconcile-duplicates.ts` (dry-run by default; `--apply` supersedes only pairs clearing the same title + compliance guards as the auto path — note its similarity default is 0.80, below the auto path's 0.86; `--include-compliance` relaxes the expiry guard). The locked archive lives in the exported `archiveWithinTx` so the endpoint, auto path, and script share identical logic + the FOR-UPDATE concurrency guard.
- Direct Redis cache: Wave 3 `chat-starters` writes a per-venue payload to `chat:starters:<orgId>:<venueId>` with a 14-day TTL via a dedicated ioredis client on `REDIS_URL` (separate from BullMQ job state and Socket.IO adapter). Flush by `DEL` on that key pattern; absent keys fall back to a generic prompt list inline.
- Third-party integrations (Square today; more later): generic `Integration` model holds encrypted per-org credentials. Encryption is AES-256-GCM with a per-record random salt + IV and HKDF-derived encryption key; ciphertext is version-tagged on disk (`v1:<base64>`) so future key/cipher rotations are non-breaking. The master key comes from `INTEGRATION_TOKEN_KEY` and MUST be prefixed `hex:` (64 hex chars) or `base64:` (44 base64 chars decoding to 32 bytes) — raw passphrases are rejected at boot. Generate one with `openssl rand -hex 32`. Providers self-register tools at `onModuleInit` against `IntegrationRegistry`; multiple providers may claim the same tool name (capability) and dispatch routes per-org via `Integration.provider`. Each provider declares a `domain` (`pos | accounting | crm | brewery | other`) and the connect endpoint refuses a second provider in the same domain for the same org. `validateCredentials` on a provider pings the vendor at connect-time so bad PATs are rejected before persistence. `ToolDispatcher` falls through to the registry on built-in tool miss, and `buildAiSdkTools` concatenates provider tool definitions onto `TOOL_DEFINITIONS`. New integrations: drop a module under `apps/api/src/modules/integrations/<provider>/`, implement `IntegrationProvider`, `register()` against the registry — no edits to `chat-tools.ts`. Venues map to a POS location via `Venue.squareLocationId`. Connect endpoint: `POST /integrations/:provider/connect-pat` (manager-only, rate-limited 10/15min/org); OAuth not yet wired but schema is OAuth-shaped (`authMode`, `refreshTokenCipher`, `tokenExpiresAt`). Per-tool per-org rate limit: 120/min (`TOOL_INVOCATION_LIMITER` in `integration-registry.ts`).
- Breww integration (`apps/api/src/modules/integrations/breww/`, domain `brewery`): read-only surface over the Breww public API (DRF-style REST at `breww.com/api/`, bearer keys prefixed `BRW.`, page/page_size pagination) — `brewery_list_batches` + `brewery_list_products` (staff), `brewery_list_purchase_orders` + `brewery_get_product_margins` (manager). The margins tool reads `/order-lines/` per-sale `product_production_cost`/`product_packaging_cost`/`margin_*` — the authoritative brewery-side production cost, and the COGS fallback when the POS catalog has no unit costs. No SDK — plain `fetch` in `breww.service.ts` (15s timeout; Breww has no `icontains` filter, so product-name matching fetches one name-ordered page and filters case-insensitively in code); connect via the generic `POST /integrations/breww/connect-pat` (validates against `/business-details/`) or the Settings card (entry in web `use-integrations.ts` `INTEGRATION_PROVIDERS`). NOT yet exercised against a live Breww account — first connect with a real key is the remaining verification.
- Square SDK (44.x) serializes UNSET optional enum query params as empty strings (`?sort_order=`) which Square 400s on GET list endpoints (devices, payouts, payments) — `scrubbingFetch` in `square-client.ts` strips empty-valued params for every call; don't remove it on SDK upgrade without re-probing (`apps/api/scripts/probe-square-endpoints.ts`). Related quirks: `vendors.search` requires a non-empty `filter` (listVendors always sends a status, default ACTIVE), and Square answers 401 "Merchant not onboarded to Appointments" for bookings on accounts without that product — `isFeatureNotOnboarded` in `square.service.ts` keeps that from tripping `markError` (which would flip the whole integration to 'error' and disable every Square tool).

- Business-aware chat: the system prompt (`apps/api/src/modules/chat/system-prompt.ts`) is parameterized, not vertical-hardcoded. Per-org business profile lives on `Organization.metadata.profile` (no column/migration — `OrganizationProfileSchema` in `types/organization.ts`: businessType, description, goals, constraints, country, currency) and is edited at `GET/PUT /org/profile` (owner/manager; `OrganizationModule`). `buildGmAgent` injects three dynamic system blocks: `<business_profile>` (persona/domain), `<operating_context>` (currency + emergency number derived from `country`, defaulting GB/£/999 so an empty profile behaves as before), and `<integrations>` (human-readable active integrations from `IntegrationRegistry.describeActiveIntegrations` — when none are connected the agent is told there are no live numbers). Chat + scheduled-report paths both load profile via `loadOrganizationProfile(orgId)`. The web Settings → Organization page has a Business profile form (`components/organization/business-profile-form.tsx`, hook `lib/hooks/use-org-profile.ts` — hand-written, NOT in the orval client; run `npm run api:generate --workspace=web` to fold it in).
- Chat tool-call UI: tool calls are NOT shown as persisted chips/accordion. While streaming, an ephemeral status line names the active tool (`toolStatusPhrase` in `components/chat/tool-labels.ts`) and clears when the answer lands. On reload, history shows answer text + deliverable cards only (report/checklist/task/stock/etc., keyed off `tool-card-router` renderers); KB tool parts (`find_knowledge`/`query_document_table`) are rehydrated invisibly to preserve the "no sources cited" trust warning. `toolCallLog` is still persisted server-side for model follow-up coherence (`expandRecentToModelMessages`) — display removal only.
- Agent memory: per-org persistent memory via the Anthropic `memory_20250818` provider-defined tool (`@ai-sdk/anthropic`). Stored as a path→content map on `Organization.metadata.memory` (no migration), sandboxed to `/memories` with size caps. Pure command engine `applyMemoryCommand` in `modules/organization/agent-memory.ts` (view/create/str_replace/insert/delete/rename); DB read-modify-write in `agent-memory.store.ts` (`handleMemoryCommand`, transactional so it never clobbers the sibling `profile` key). Wired into `buildGmAgent` via the optional `memoryExecute` closure — enabled for interactive chat only (NOT headless scheduled reports), and the `<memory>` prompt block is injected only when the tool is present. Disable org-wide with `AGENT_MEMORY_DISABLED=1`. Memory is for durable operating preferences/facts — NOT a replacement for the KB (SOPs → `save_knowledge_doc`), tasks, or notes; the `<memory>` prompt block enforces precedence (KB/live tools/owner always override memory; memory is never cited and never gates capability) so the two stores can't clash. Both `handleMemoryCommand` and `OrganizationService.updateProfile` write their own metadata subkey via `jsonb_set` under a `SELECT … FOR UPDATE` row lock, so concurrent memory/profile writes never lose updates. Staleness hygiene: `MemoryReconcileModule` (BullMQ `memory-reconcile` queue) prunes memory notes the KB now contradicts/covers via a conservative Haiku pass — a nightly fanout over orgs with non-empty memory PLUS a debounced per-org trigger (`MemoryReconcileTrigger.onKbChanged`, 5-min coalesce) fired when a doc reaches `ready` or is superseded (`docs.service` + `reconcile.service`). Read-time precedence already prevents stale answers; reconcile only purges lingering notes. Flags: `MEMORY_RECONCILE_CRON_DISABLED=1` (cron + trigger), `MEMORY_RECONCILE_GENERATOR_DISABLED=1` (skip the Haiku call).

## Review Gate

Before declaring any code-edit task complete in `apps/api/src/` or `apps/web/src/`, spawn `code-reviewer` and `security-reviewer` (parallel — one message with multiple Agent tool blocks). For doc or API-contract changes, also spawn `doc-reviewer`. Surface every HIGH/MEDIUM finding before closing the work.

Skip only for: pure doc edits, formatting-only changes, dependency bumps with no code impact, single-line config knob changes.

## Don'ts

- Never modify existing Prisma migrations under `apps/api/prisma/migrations/`. Add a new one.
- Don't edit `apps/web/src/generated/**` (orval-generated API client).
- `docs/` xlsx files are runtime canaries for the document-intelligence pipeline, not dev seed data.
