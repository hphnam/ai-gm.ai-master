<objective>
## Goal
Ship phone-number linking end-to-end — an authenticated user enters an E.164 phone number in `/settings/phone`, receives a 6-digit SMS OTP via Twilio Verify, submits the code, and on success has `User.phoneNumber` + `User.phoneVerifiedAt` persisted. Any subsequent sign-in by the same user shows the phone as verified. Concurrent sessions on different devices share the same verified state. A user can unlink their number to link a different one. Numbers are unique across all users — a number already linked to another account fails explicitly. Rate limits prevent SMS abuse.

## Purpose
Plan 01-01 shipped auth + orgs and Plan 01-02 shipped team invitations. Phase 3 (WhatsApp Integration) needs a way to map an inbound `From: +447...` WhatsApp number back to a `User → Organization → Venue` chain — phone-linking is the only primitive that enables that lookup without forcing every WhatsApp message through a magic-link dance. This plan turns the dormant `User.phoneNumber` / `User.phoneVerifiedAt` columns (already in schema from 01-01) into a working verification flow, and is the last v0.2 Phase 1 plan before Phase 2 (Document Ingest UI).

Per-message SMS costs make rate-limiting a higher priority than the email equivalent (01-02). Twilio Verify is chosen over rolling our own OTP storage because (a) Twilio handles code generation / expiry / attempt counts server-side, removing a whole class of cryptographic bugs from our surface, (b) their per-number and per-IP rate limits are production-grade out of the box, (c) swap-out to alternate verification channels (voice, WhatsApp OTP) is a Twilio config change not a code rewrite.

## Output
- NestJS `PhoneModule` exposing:
  - `POST /auth/phone/send` — authenticated; body `{ phoneNumber }` (E.164). Initiates Twilio Verify start. Returns `{ ok: true, expiresInSeconds: 600 }` on success. Rate-limited per user + per number.
  - `POST /auth/phone/verify` — authenticated; body `{ phoneNumber, code }`. Calls Twilio Verify check; on approval sets `User.phoneNumber` + `User.phoneVerifiedAt` in a single transaction with uniqueness check. Returns `{ ok: true, phoneNumber, phoneVerifiedAt }`.
  - `DELETE /auth/phone` — authenticated. Clears `phoneNumber` + `phoneVerifiedAt` for the current user. Returns `{ ok: true }`.
  - `GET /auth/phone/status` — authenticated. Returns `{ phoneNumber: string | null, phoneVerifiedAt: string | null }` for the session user.
- `TwilioVerifyService` wrapping Twilio Verify REST API with console driver fallback (mirroring `MailService` console mode from 01-02).
- Extended `assertAuthEnv` reading optional `TWILIO_ACCOUNT_SID` + `TWILIO_AUTH_TOKEN` + `TWILIO_VERIFY_SERVICE_SID` (all-or-nothing: either all three present → live driver, or all three absent → console fallback; partial config → fail-fast).
- `TWILIO_DRIVER_OVERRIDE='console'` env var forcing console mode even when live creds are set (for probe runs + local dev without burning SMS credit). Mirrors `MAIL_DRIVER_OVERRIDE` from 01-02.
- Next.js `/settings/phone` page (authenticated) — status card showing current verified number (if any) + link/unlink affordance + two-step send→verify form with inline error messaging.
- `probe-auth.ts` extended P22–P27 covering: happy-path link, wrong-code reject, phone-already-linked conflict, driver-override console path, per-user rate limit, concurrent-verify race.
- `.env.example` + `packages/types/src/api.ts` append `phone-invalid-format` / `phone-already-linked` / `phone-verification-failed` / `phone-rate-limited` / `phone-service-unavailable` / `phone-not-linked` error codes.

## AC-1: Authenticated user sends verification code

```gherkin
Given an authenticated session for a user with no linked phone
When the client POSTs /auth/phone/send with { phoneNumber: "+447700900123" }
Then Twilio Verify is called with channel='sms' and the number
And the response body is { ok: true, expiresInSeconds: 600 }
And a structured log `phone.verify_sent` is emitted with { userId, phoneHash, requestId }
And the raw phoneNumber is NEVER written to any log (only sha256-prefix-16 hash)
```

## AC-2: User verifies with correct code; phone persisted

```gherkin
Given an authenticated session for a user with no linked phone
And /auth/phone/send was called for "+447700900123" (stub returns ok)
When the client POSTs /auth/phone/verify with { phoneNumber: "+447700900123", code: "123456" }
And Twilio Verify returns status='approved'
Then the User row is updated: phoneNumber = "+447700900123", phoneVerifiedAt = now()
And the response body is { ok: true, phoneNumber: "+447700900123", phoneVerifiedAt: "<iso>" }
And a structured log `phone.verified` is emitted with { userId, phoneHash }
```

## AC-3: Wrong code fails without persisting phone

```gherkin
Given an authenticated session
When the client POSTs /auth/phone/verify with code that Twilio Verify returns status='pending' or the check throws 404
Then the response is 400 with { error: "phone-verification-failed" }
And the User row phoneNumber / phoneVerifiedAt are unchanged (null)
```

## AC-4: Phone already linked to another user rejects verify

```gherkin
Given user A has phoneNumber = "+447700900123" linked
And user B has a pending Twilio Verify for "+447700900123"
When user B POSTs /auth/phone/verify with the correct code
Then the response is 409 with { error: "phone-already-linked" }
And user B's User row phoneNumber remains null
And user A's User row is unchanged
And a structured log `phone.already_linked_blocked` is emitted { attemptingUserId, ownerUserId, phoneHash }
```

    - `startVerification(phoneNumber: string): Promise<{ ok: true; mode; sid?: string } | { ok: false; reason: 'phone-service-unavailable' | 'phone-invalid-format' }>`. Console mode: emit `phone.console_fallback` log with `{ phoneHash, code: 'PROBE-<last-6-of-phone-digits>' }` deterministic code; return ok. Console mode: `approved = (code === 'PROBE-<last-6-digits>')`. Live mode: POST to `.../VerificationCheck` with `{ To, Code }`, 10s AbortSignal. 2xx with status='approved' → approved=true. 2xx with status≠approved OR 404 → approved=false.
